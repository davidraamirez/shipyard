# Plan: real app deployments (v1, Docker)

Branch: `feat/app-deployments` · Status: **agreed, not started**

## Context

Today a deployment clones the repo, builds it in an isolated container, deletes the workspace and sets `RUNNING`. Nothing is kept or running, so `RUNNING` only means "build succeeded". This feature makes a successful deployment produce a running app reachable at a URL.

v1 targets **Docker on the same host** and must be stable. **Kubernetes comes in a later iteration**, so every piece below is chosen to be portable (see [Kubernetes readiness](#kubernetes-readiness)).

## Decisions

| Topic | Decision |
|---|---|
| Runtime | Docker on the same host, through the existing `docker-proxy` |
| Packaging | One container image per deployment, built from a Dockerfile generated by Shipyard |
| App types | Static sites and Node servers |
| URLs | One subdomain per project: `http://<slug>.localhost:8080` via Traefik (port configurable) |
| Who deploys | The existing `build-runner` (single Docker-privileged service) |
| Previous releases | One app container per project; the previous deployment becomes `STOPPED`; keep the last 3 images per project, delete older ones |

## Architecture

```
worker ─ clone ─ build ─ detect app type ─ DEPLOYING ─ POST /releases ─ RUNNING (url)
                                                           │
                                              build-runner (Runtime: Docker)
                                    ┌──────────────────────┴───────────────────────┐
                               image build                                  app container
                     (generated Dockerfile, COPY only)          network shipyard_apps, healthcheck,
                                                                 Traefik labels
                                                                       │
                              Traefik ◄── docker-proxy (read-only) ────┘
                                 │
                       http://<slug>.localhost:8080
```

### App type detection (worker, after the build)

1. An `index.html` in `dist/`, `build/` or `out/` → **static** (output dir = the first match).
2. Otherwise a `start` script in `package.json` → **node**.
3. Otherwise → `PermanentDeploymentError("Nothing to deploy: …")`.

### Images

The runner writes the Dockerfile itself; the repo's own Dockerfile is never used and no user code runs during the image build (only `COPY`).

- **static**: unprivileged nginx image, serves the output dir, SPA fallback to `index.html`, listens on 8080.
- **node**: `node:22-alpine`, copies the workspace (without `.git` and Shipyard caches), runs `<manager> start` as user `node`, with `PORT=8080`.
- Tag: `shipyard-app-<slug>:<deploymentId>`, labeled with project and deployment.
- The build context is a tar created by the runner from the workspace: regular files and directories only, symlinks are not followed, size limit.

### Running apps

- One container per project, `shipyard-app-<slug>`, on network `shipyard_apps` (internet egress, isolated from the compose network: no access to Postgres, Redis, API, runner or Docker).
- Same hardening as build containers: non-root, read-only rootfs + tmpfs `/tmp`, `CapDrop: ALL`, `no-new-privileges`, memory/CPU/PID limits.
- A container healthcheck (HTTP on `PORT`) decides readiness: the new container must be healthy before the old one is stopped. If it never becomes healthy, the deployment fails and the previous app keeps running.
- Traefik routes `Host(<slug>.localhost)` using container labels, reading Docker through a second, read-only `docker-proxy`.

### Runner API (build-runner)

| Endpoint | Purpose |
|---|---|
| `POST /releases` | Build the image and start the app (async, 202, same polling pattern as `/builds`) |
| `GET /releases/:deploymentId?after=N` | Status + incremental output |
| `POST /apps/:slug/stop` | Stop the project's app |
| `DELETE /apps/:slug` | Stop and remove its container and images (project deleted) |

### Data model

- `Project.slug`: unique, `[a-z0-9-]`, derived from the name; existing projects are backfilled in the migration.
- `Deployment.url`, `Deployment.imageTag` (nullable).
- `DeploymentStatus.STOPPED`: a deployment that was running and has been replaced or stopped.
- Lifecycle: `QUEUED → BUILDING → DEPLOYING → RUNNING → STOPPED`, or `FAILED` from any active state.

## Security

- `docker-proxy` gains `BUILD=1` (image builds). Mitigation: the runner generates both the Dockerfile and the build context; nothing from the request reaches them unvalidated (slug and deployment id are validated, the output dir comes from a fixed list).
- Running user code long-term is riskier than building: apps get their own network and no secrets from Shipyard's environment. This is still container isolation, not a sandbox (same caveat as builds; production needs gVisor/Kata or K8s with policies).
- Traefik only gets read access to Docker.

## Kubernetes readiness

v1 must not block the move to Kubernetes:

- The worker talks to a `Runtime` interface (`deploy`, `stop`, `remove`, `status`); Docker is its first implementation.
- Images are the artifact (a registry is added with Kubernetes; Docker v1 uses local images).
- Healthcheck → readiness probe; Traefik labels → Ingress; one container per project → one Deployment per project.
- Apps get their config through env (`PORT`), never host paths.

## Steps

Each step is a checkpoint: tests green, reviewed, committed by the user.

1. **Data model**: migration (`slug`, `url`, `imageTag`, `STOPPED`), API returns them, slug generated on create. *Done when* existing projects have slugs and API tests pass.
2. **Infrastructure**: `shipyard_apps` network, Traefik service on 8080, read-only proxy, `BUILD=1`. *Done when* a manually started container with labels is reachable at `http://test.localhost:8080`.
3. **Image packaging** (runner): tar context + generated Dockerfiles + image build. *Done when* unit tests cover the Dockerfiles/context rules and a real image builds for both test repos.
4. **Running apps** (runner): app container spec, healthcheck wait, replace old container, stop/remove, image cleanup (keep 3). *Done when* security-spec tests pass and replace/rollback-on-unhealthy work against real Docker.
5. **Worker**: app type detection, `DEPLOYING` step through the `Runtime` interface, `STOPPED` for the previous deployment, error classification. *Done when* processor tests cover each path.
6. **API + web**: show URL and an "Open app" button, stop app, delete project removes the app. *Done when* the full flow works from the browser.
7. **End to end**: `github/codespaces-express` (node) and `github/codespaces-react` (static) reachable at their URLs; redeploy replaces the app; failed health keeps the old one. CLAUDE.md updated.

## Out of scope (v1)

Kubernetes and an image registry, custom domains and HTTPS, environment variables/secrets per project, rollback UI (images are kept to make it possible), preview deployments per commit, autoscaling.
